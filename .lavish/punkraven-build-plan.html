This session

The theme layer was rebuilt from scratch

Dark mode was added, then the band system that phase 1 introduced was deleted entirely. The site now runs one uniform light theme and one uniform dark theme, and sections differentiate by elevation rather than by polarity.

What went away

  • The band system - <Band tone="paper|pure|ink">, the three .band--* classes, components/band.tsx.
  • Six token blocks and the key-parity contract between them.
  • 125 lines restating HeroUI's derived-token formulas per band.
  • Every dark: utility - none remain in the codebase.
  • Spec §5.1's alternating bands, deliberately overridden.

What replaced it

  • <Section elevation="base|sunken"> - elevation, never polarity.
  • Two token blocks, :root and :root.dark, 25 keys each.
  • next-themes with a two-state toggle defaulting to the OS.
  • Two elevation ladders, both hue 264 with chroma held constant.
  • globals.css went 806 → 354 lines.

The elevation ladders

raised · cards, header#F4F8FF
base · page default#E4E8EF
sunken · hero, CTA, footer#CFD8EA
raised · cards, header#191D25
base · page default#0E121A
sunken · hero, CTA, footer#05080F

ΔL 0.048 between adjacent rungs, above the 0.045 perceptibility floor. Each rung shifts ΔL ~0.748 between themes, so every section visibly changes on toggle - the defect that started the rebuild.

The amber rule survived every rewrite

Spec §5.2 reserves the amber for uncertainty, status and unverified claims only. It is still not exposed through @theme, so no bg-uncertain utility is generated - confirmed as zero occurrences in the compiled CSS. Only statusChip and sectionRule can reach it.

Settled

Decisions taken - do not re-litigate

Product and copy

  • T&T powers LawSafe - confirmed, so the dependent-stack framing stands.
  • Reuse the existing raven logo as the wordmark. Still needs a favicon.
  • The form is UI-only - renders and validates, no backend.
  • Every statistic is held until an owner verifies it.
  • The nine Indic strings come from a human, not a machine.
  • Build the full LawSafe page per spec §3.4.

Design and architecture

  • Orbitron is display only - latin-only, and cannot render Indic script, §, ₹ or →.
  • Circuit board only where a node graph illustrates content, with a reduced-motion guard.
  • Dark mode exists, reversing the earlier removal.
  • Uniformity over alternation - light mode all light, dark mode all dark, overriding §5.1.
  • The teal is semantic, not a primitive - one shared value would have been muddy in both themes at a threshold margin.
  • The sticky header separates by border, never by fill - no fill works when a card scrolls under it at the same elevation.
Risk

What could still go wrong

The copy is a minefield

Claim gates use no literal "needs verification" string, so a grep finds nothing and passes pages that should fail. Read each Part C and D table by hand.

NyayaSetu leaks

Deleting LawSafe §0 does not remove it - two of four occurrences sit outside that section. grep -ri nyayasetu the whole tree before shipping /lawsafe.

Competitor names survive

§6 is in scope and names GPT-4, Llama 2, PaLM 2, Lexis+ AI and Westlaw with fabrication rates. Keep the principle, drop the names and percentages.

The font chain looks like dead code

import "@/config/fonts" in _app.tsx has no binding and is load-bearing. Removing it empties every font variable silently.

Key parity fails at runtime

:root and :root.dark must declare the identical key set. A key missing from the dark block keeps its light value with no build error.

The amber erodes quietly

It is protected by not generating a utility. Adding the theme key back would let amber be authored anywhere, and it degrades across surfaces without failing loudly.

Static site, no backend. "Verified" means build, typecheck and lint pass and the change was confirmed in a real browser. The browser leg is currently held, so nothing in the theme rebuild meets the full bar yet.
